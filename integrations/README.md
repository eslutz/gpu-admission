# Worker integration

A GPU Admission worker is the code that knows when a GPU job starts and when every process using that job’s GPU resources has exited. The tray coordinates workers through local files.

## Docker worker

Copy `gpu_admission_client.py` into your worker image. Use the Compose mounts generated by the app, then run the connection test inside the container.

```sh
python3 gpu_admission_client.py probe /admission/read /admission/request video-worker
```

To integrate jobs, follow this sequence:

1. Create `Worker("/admission/read", "/admission/request", "video-worker")`. Call `worker.acquire(minimum_free_vram_mib=4096)` before claiming or launching GPU work. If it returns `None`, defer and retry through your own scheduler.
2. Immediately before starting the job, call `lease.can_start()`. If it returns false, call `lease.release()` and defer.
3. Launch the job. Call `lease.mark_running()`, then call `lease.heartbeat()` at least every five seconds while the workload is active.
4. Call `lease.release()` after the whole GPU workload exits. If you cancel a job, finish stopping it before releasing. If the worker loses its own state and cannot prove the job ended, leave ownership intact and reconcile it.

The worker can call `worker.announce()` while idle, even in Hold. This optional heartbeat lets the tray show **Connected / idle**. The reference client uses the standard library; an existing worker can implement the same contract in its own language.

### File contract

- Read `/admission/read/status.json` and `/admission/read/grants/<worker-id>.json`. Check that the status shows global and worker **Auto**.
- Write `<request_id>.json` under your own request mount. Write a temporary file in the same directory and atomically rename it into place.
- Use a new 32-character lowercase hexadecimal request ID. Your request starts as `requested`; after a matching `reserved` grant, write `active`. Start work only after a matching fresh `active` grant and a final check of both modes.
- Match schema, consumer, request ID, GPU ID, and generation on grants and active status. Both status and grants must be no more than 15 seconds old. Use integer Unix seconds for request timestamps.
- For presence, use `presence/heartbeat.json` inside the worker’s request directory. The schema is `gpu-admission-presence/v1`; include `consumer`, `session_id`, `generation`, `observed_at`, and `phase` (`idle`, `waiting`, or `running`). Running presence uses the active request ID as the session ID.
- A Docker worker can include its own exact container ID or Docker’s default 12-character container hostname in `docker_instance`. The guard can then bind the request to that immutable instance. An inspection of the exact saved container ID is required to confirm a Docker stop.

#### Example v1 request

```json
{
  "schema": "home-network-gpu-admission/v1",
  "consumer": "video-worker",
  "request_id": "0123456789abcdef0123456789abcdef",
  "generation": "<from status.json>",
  "gpu": "<from status.json>",
  "state": "requested",
  "observed_at": 0,
  "heartbeat_at": 0,
  "minimum_free_vram_mib": 4096
}
```

## Recovery required

Pause admission before investigating. Ownership can survive a tray or worker restart. A missing heartbeat or a container with the same name is insufficient to clear it.

1. Check the worker’s logs and the tray’s log folder. Identify the worker and the original request.
2. Confirm that its complete GPU job has ended. For a container, confirm the original instance, including its container ID. For Windows, terminate or wait for the runner and confirm that its contained workload is gone. If the workload can launch outside that process tree, check those processes on the host as well.
3. If the worker is available, use its normal release path with the exact original identity. A replacement worker must recover the original request data and prove the workload stopped before issuing a matching release. Keep Hold while checking that the tray clears the owner.
4. If the original request or proof is missing, keep the profile in Hold until it can be reconciled with the operator who manages that worker. Preserve the journal and requests for diagnosis.

Windows launcher exit code `3` means no work started. Exit code `2` indicates an invalid or already running worker. Once the process starts, its exit code is returned after the process tree empties.
